Границы проекта

Одна миграция переносит один workload с одной площадки A на заранее подготовленную площадку B. Workload — приложение и его журнал данных с единственным писателем. Реплика существует до тревоги. Миграция нескольких приложений, физическая безопасность, определение угроз, автоматический failback и аварийное восстановление с допустимой потерей данных исключены из MVP.

Сценарий — плановая подготовка к возможному отключению, пока источник доступен. Внезапная потеря A до финальной синхронизации переводит процесс в BLOCKED. Система не обещает восстановить данные, которых нет на B.

Контур управления расположен вне отключаемой площадки. Он сохраняет состояние миграции даже при остановке A. Пять отдельных хранилищ принадлежат пяти сервисам. В учебной сборке они могут быть отдельными БД одного PostgreSQL, что не обеспечивает отказоустойчивость самого хоста.

Инварианты

  • I1: одновременно не больше одного действительного разрешения на запись для workload.
  • I2: B получает право записи только после подтверждённого fencing A и применения финального checkpoint.
  • I3: сумма HELD + PINNED + ALLOCATED ресурсов не превышает ёмкость B.
  • I4: повтор команды не создаёт повторного эффекта, старое поколение операции отвергается.
  • I5: READY_TO_SHUTDOWN возможен только для текущего поколения после проверки маршрута, состояния B, fencing A и завершённых задач персонала.
  • I6: неопределённый результат операции не считается отказом и не запускает противоположную операцию автоматически.

Это проектные требования. Их проверка реализацией описана в плане второй части.

1. Карта контекстов

Предметная область

«Летающий мопед» — шуточное название внешнего повода для аварийной готовности. Внутри системы используется нейтральное событие тревоги. Заказчик — оператор нескольких дата-центров, дежурный запускает подготовку, инженер подтверждает задания площадки.

Почему микросервисы

Здесь разные владельцы ресурсов и интеграций: диспетчер инцидентов, команда вычислительных мощностей, команда хранения, команда сетевого переключения и эксплуатация площадок. Резервирование обслуживает также обычные развёртывания, репликация работает постоянно, эксплуатационные задания живут часами, переключение требует узких привилегий. Их изменения и отказы должны изолироваться. Общая БД не делает атомарными внешнее переключение, репликацию и действия людей.

Монолит для учебного масштаба возможен. Мы не утверждаем математическую необходимость микросервисов: выбор оправдан предположением о нескольких площадках, независимых командах и уже существующих инфраструктурных контурах. Если этих условий нет, модульный монолит дешевле. Для задания явно принимаем эти условия и демонстрируем распределённую координацию.

Incident Service — инциденты

Владеет тревогами, миграциями, состоянием saga, дедлайнами, журналом решений и idempotency/inbox/outbox. Уникальный активный процесс на workload исключает конкурирующие миграции. Отдельный сервис нужен для длительной координации и восстановления после перезапуска. Он решает, какой шаг нужен, но не назначает сам право записи и не владеет инфраструктурой.

Capacity Service — резервирование

Владеет лимитами CPU/RAM, резервами и их состояниями HELD, PINNED, ALLOCATED, RELEASED, EXPIRED. Проверяет ёмкость и создаёт резерв в одной транзакции с блокировкой строки пула. Отдельный контекст позволяет использовать ресурсы и для других заказчиков, независимо от инцидентов. Только этот сервис меняет учёт доступной мощности.

Data Protection Service — защита данных

Владеет проверками репликации и доказательствами применения checkpoint, но не бизнес-данными приложения. Адаптер обращается к внешнему контроллеру хранения. Отдельная граница изолирует специфичные для СУБД проверки timeline, checkpoint и целостности. Успех проверки связан с migrationId, generation, freezeId, source, target и checkpoint; его нельзя применить к другой миграции.

Traffic Service — переключение

Владеет операциями freeze, promote, route и resume, их внешними operationId и наблюдаемыми результатами. Обращается к контроллеру права записи и маршрутизации. Отдельный сервис ограничивает круг компонентов, способных остановить запись или сменить писателя. Долговечный fencing обеспечивает внешний контроллер, а не значение в таблице Traffic.

Readiness Service — готовность

Владеет заданиями персоналу, версией чек-листа и разрешением на плановое отключение конкретной площадки. Отделён из-за человеческого жизненного цикла и собственного доступа инженеров. Он самостоятельно перепроверяет доказательства у Capacity, Data и Traffic. В MVP выдаёт разрешение и показывает его оператору, физическое отключение не выполняет.

Связи контекстов

Incident — потребитель опубликованных REST-контрактов четырёх сервисов. Все пять публикуют факты через RabbitMQ; событие ускоряет реакцию, но перед опасным действием нужна актуальная проверка владельца состояния. Capacity, Data и Traffic являются upstream-поставщиками доказательств для Readiness. Внешние API скрыты за адаптерами Data и Traffic (anti-corruption layer). Общая библиотека бизнес-моделей и доступ к чужим таблицам запрещены.

Исходник: context-map.mmd.

2. C4 Container

Исходник: containers.mmd. C4 представлен Mermaid flowchart: граница системы, тип и технология каждого контейнера, назначения связей и внешние системы явно подписаны.

Контейнер Технология для второй части Ответственность
Operator UI Простая веб-страница Тревога, прогресс, задания
Incident / Capacity / Data / Traffic / Readiness Java 21, Spring Boot, пять процессов Контексты из карты
Пять сервисных БД PostgreSQL Только локальные ACID-транзакции

Replication Controller, внешний REST API; в демо тот же процесс симулятора Применение checkpoint на B
Threat Feed, внешний REST-клиент; в демо симулятор Идентифицированная тревога

Симулятор может совмещать два внешних API в одном процессе, но их ответственность разделена. Пользовательские данные A/B находятся за внешними контроллерами, а не в сервисных БД нашей системы. UI не является шестым бизнес-сервисом.

Размещение и отказы

Production-допущение: API и устойчивые хранилища контура управления переживают потерю A. RabbitMQ использует три узла и quorum queues, узлы управления размещаются в независимых доменах отказа. Это целевая топология, не обещание учебного Docker Compose. Контроллер права записи тоже должен иметь независимое устойчивое состояние и исключать split brain.

В демо всё работает на одном компьютере. Проверяем падение процессов, дубли и сетевые ошибки, но не доказываем устойчивость к разрушению площадки. Сбой сервисной БД останавливает соответствующий сервис, не разрешает ему продолжать действия «из памяти».

Нефункциональные требования

  • Safety важнее доступности во время переключения: неизвестное fencing или checkpoint означает BLOCKED.
  • Проектная цель демо: восстановить работу оркестратора за 30 секунд после его перезапуска; цель измеряется, не является SLA.
  • Предварительный дедлайн подготовки 120 секунд, окно freeze 30 секунд, сверка каждые 5 секунд. Значения конфигурационные и требуют испытаний.
  • Наблюдаемость: migrationId, commandId, generation и traceId в логах; метрики возраста outbox, отставания saga, времени без writer, DLQ и зависших резервов.
  • TLS/mTLS между сервисами в целевой среде, JWT с audience и ролями. Токены не передаются через события. В демо dev-учётные записи явно отделены от production.

3. Контракты

Машиночитаемые спецификации: OpenAPI 3.1 и AsyncAPI 3.0. JSON выбран для проверки стандартным парсером, это полноценный формат обеих спецификаций.

REST

Единый файл описывает несколько серверов; операция явно указывает сервис назначения. HTTP-вызовы принимают долговечную команду и быстро возвращают 202 с operationId. Длительная работа выполняется после фиксации. GET operation позволяет узнать результат, не полагаясь на уведомление.

Каждый POST требует Idempotency-Key. Область ключа: caller + HTTP method + path + key. Тот же ключ и тело возвращают ту же операцию; другой payload — 409. Создание команды, запись ключа и outbox атомарны. commandId задаётся клиентом до первого запроса и позволяет искать операцию после потери 202. Результаты и ключи хранятся минимум до завершения инцидента плюс 30 дней, а уникальность бизнес-идентификаторов сохраняется постоянно. После периода ключей повторы старых поколений отвергаются доменными ограничениями.

operationId совпадает с commandId для всех команд MVP. GET /operations/{operationId} вызывается на том же сервисе. SUCCEEDED означает, что выполнена именно команда action, а не что вся миграция завершена. UNKNOWN требует readback. FAILED возможен только при подтверждённом отсутствии эффекта либо доменном отказе. У всех ошибок есть code, detail, retryable, traceId.

Реестр команд

Получатель action Предусловие / результат
Capacity RESERVE Есть свободные units; HELD на 120 секунд
Capacity PIN HELD ещё действителен; бессрочный PINNED до разрешения процесса
Capacity ALLOCATE PINNED и подтверждено назначение B writer; ALLOCATED
Capacity RELEASE HELD можно освободить; PINNED только после закрытого abort на A; после promote запрещено
Data PRECHECK Реплика существует, совместима, доступна
Data VERIFY freezeId известен, B применил checkpoint нужного timeline
Traffic FREEZE Резерв PINNED; долговечное запрещение записи A, дренирование, финальный checkpoint
Traffic PROMOTE Freeze подтверждён, Data proof актуален, резерв PINNED; B получает epoch + 1
Traffic ROUTE B — текущий writer, health-check успешен; маршрут и readback подтверждены
Traffic RESUME Только атомарный abort контроллера до promote; A получает новое epoch
Readiness CHECK Чек-лист завершён, проверки всех владельцев успешны; разрешение текущему поколению

Все команды несут migrationId, workloadId, generation и commandId. generation — монотонный номер процесса на workload, назначенный Incident; writerEpoch — независимый монотонный номер контроллера права записи. Их нельзя подменять друг другом. Сервисы сверяют принадлежность команд и полномочия вызывающего.

Только Incident вызывает управляющие команды, инженер вызывает POST task completion, Readiness читает доказательства. Traffic сам проверяет резерв и Data proof перед PROMOTE. Capacity перед RELEASE для PINNED получает через Traffic доказательство, что контроллер навсегда закрыл эту generation как ABORTED. Просто увидеть writer=A недостаточно: запоздалый FREEZE ещё мог бы исполниться. Неизвестное состояние запрещает освобождение PINNED. Readiness повторяет проверки непосредственно при выдаче разрешения.

События

Пять типов фактов: IncidentChanged, CapacityChanged, DataChecked, TrafficChanged, ReadinessChanged. Каждый публикуется только сервисом-владельцем. Envelope включает eventId, occurredAt, migrationId, generation, aggregateId, aggregateVersion, causationId, traceId, schemaVersion=1. Payload перечисляет допустимые состояния.

Exchange moped.events (topic), routing key совпадает с адресом AsyncAPI channel. Отдельная durable quorum queue на каждого подписчика: incident.events, readiness.events. Incident получает события остальных четырёх сервисов; Readiness получает Incident, Capacity, Data, Traffic. События Readiness возвращают прогресс в Incident. Нет общего конкурирующего consumer queue для разных контекстов.

Публикация persistent, mandatory и publisher confirms. Outbox остаётся непереданным при return/nack/тайм-ауте. Consumer фиксирует inbox(eventId UNIQUE) и изменение своей проекции одной транзакцией, затем ACK. Дубли допустимы. Пропуск aggregateVersion запускает GET владельца; устаревшее событие не откатывает состояние. Ни глобального порядка, ни exactly-once не обещаем.

Retry с backoff и jitter: 1, 2, 4, 8, 16 секунд; затем DLQ и сигнал оператору. Исправленное событие переигрывается с исходным eventId, если оно не было обработано успешно. Семантически новое действие получает новый commandId. Сверка операций продолжает работать даже при недоступном брокере.

Внешние контракты

OpenAPI также описывает минимальный Simulation Adapter API. Это проектный контракт для второй части, а не существующий промышленный продукт. Контроллер обязан сохранять команды и фактическое состояние между рестартами. FREEZE и PROMOTE выполняются как идемпотентные переходы на workload с compare-and-set по generation/epoch. PROMOTE и RESUME сериализуются: победа одного делает другой конфликтом. RESUME также умеет закрыть попытку до FREEZE: freezeId тогда отсутствует, source и expectedEpoch должны совпасть с действующим A. Контроллер сохраняет tombstone ABORTED для generation, даже если ещё не видел FREEZE. Любой поздний FREEZE/PROMOTE этого поколения отклоняется. Более новая generation принимается только после завершения предыдущей попытки и проверки текущего writer.

Freeze возвращает checkpoint только после остановки приёма записи A и завершения/отмены уже принятых транзакций. Fencing сохраняется после рестарта A. Старые прямые соединения также блокируются. Смена DNS сама по себе этого не обеспечивает. В демо запись идёт только через симулятор, где эти условия проверяются атомарно.

Примеры

examples.json содержит POST тревоги, команду резервирования и событие. Все UUID иллюстративные. Перед реализацией версии библиотек фиксируются в сборке; текущие файлы задают договорённость команды.

4. Главный процесс

Sequence-диаграммы показывают логические команды и конечные результаты. Для компактности промежуточные HTTP 202 и повторные GET operation опущены, кроме шага, где их важно показать. Фактический транспорт всех длительных операций задан в OpenAPI.

Успех

  1. Threat Feed присылает alertId. Incident атомарно создаёт миграцию и generation. Повтор alertId возвращает её; другая тревога для активного workload присоединяется к существующему процессу.
  2. Capacity резервирует ресурсы HELD. Data проверяет совместимость готовой реплики. Readiness создаёт обязательные задания при событии создания миграции либо при CHECK с ленивой инициализацией.
  3. Capacity переводит резерв в PINNED. После этого время само не освобождает его.
  4. Traffic вызывает FREEZE: A прекращает запись, дренирует транзакции, фиксирует долговечный fence и финальный checkpoint. Если подтверждение потеряно, выполняется readback.
  5. Data доказывает применение этого checkpoint на B. Проверка «lag = 0» до freeze недостаточна: между проверкой и остановкой могла пройти новая запись.
  6. Traffic проверяет proof и резерв, затем PROMOTE присваивает B новое writerEpoch. Контроллер сохраняет факт перехода до возврата результата. A остаётся fenced.
  7. Traffic переводит маршрут на B и делает readback/health-check. Capacity фиксирует ALLOCATED.
  8. Инженер завершает задания. Readiness проверяет текущие proof, writer, маршрут, fence и резерв. Выдаёт разрешение READY_TO_SHUTDOWN. Incident фиксирует результат. Автоматического отключения в MVP нет.

Сбой 1: мощности не выделены

Capacity подтверждает NO_CAPACITY. Freeze ещё не запускали. Incident завершает процесс ABORTED, подтверждённые частичные резервы освобождает. В MVP один резерв атомарен, поэтому частичный резерв внутри него невозможен. Если ответ Capacity потерян, Incident сначала получает исход операции по commandId, затем освобождает найденный HELD; повтор не создаёт второй резерв.

Сбой 2: реплика не догнала checkpoint после freeze

Процесс не разрешает PROMOTE. После дедлайна Incident переводит процесс в BLOCKED, запрашивает RESUME. Контроллер атомарно закрывает попытку миграции как ABORTED и возвращает право записи A с новым epoch, только если PROMOTE не произошло. Запоздалый PROMOTE с этой generation отклоняется. Затем Capacity освобождает резерв. Если контроллер недоступен, A остаётся fenced, резерв PINNED, статус BLOCKED и вмешательство дежурного. Потеря доступности предпочтительнее двух писателей.

Сбой 3: promote состоялся, ответ потерян, Traffic упал

B уже writer с epoch 42. Incident не знает результата и не запускает RESUME. После рестарта Traffic читает контроллер по исходному commandId, восстанавливает SUCCEEDED и outbox. Дальше повторяет ROUTE идемпотентно, резерв становится ALLOCATED, Readiness завершает проверки. Если маршрут долго недоступен, B остаётся единственным writer, система DEGRADED, отключение A ещё не разрешено. Обратный перенос — отдельная будущая миграция после синхронизации, не компенсация этой saga.

Состояния и точка невозврата

BLOCKED сохраняет lastSafeStep и pendingCommandId; переход из него разрешён после авторитетной сверки. DEGRADED означает, что B уже writer, но маршрутизация или проверки ещё не завершены. READY_TO_SHUTDOWN — успех подготовки, не утверждение о физическом выключении A.

До promote возможна компенсация RESUME с атомарным закрытием попытки. После promote возможны повтор, сверка и завершение вперёд. Тайм-аут не доказывает, что promote не случился.

Гарантии данных

RPO=0 относится к успешному плановому переносу при доступном A и выполненном финальном барьере. Для внезапной потери A при асинхронной репликации это неверно. Возможное расширение — синхронное подтверждение записи на независимой площадке, но оно меняет задержки и доступность. RTO не ограничен сверху при длительном отказе контроллера или отсутствии мощности.

Каждый ADR содержит контекст, альтернативы, решение и последствия. Это принятые проектные решения, их реализация относится ко второй части.

ADR-001: Границы контекстов и собственные БД

Статус: принято для учебного проекта. Дата: 2026-10-27.

Контекст

Разные команды управляют ресурсами, репликацией, переключением и заданиями. Общая транзакция не охватывает инфраструктуру.

Варианты

Модульный монолит; пять сервисов с общей БД; пять сервисов с отдельными БД.

Решение

Пять сервисов с отдельными БД и REST/событиями. Координация в Incident. В демо один PostgreSQL допускается только как хост отдельных БД.

Последствия

Независимые права и отказы, но больше развёртываний и eventual consistency. Для маленькой реальной команды монолит мог бы быть экономичнее.

Когда пересмотреть

Слияние контекстов допустимо при исчезновении независимых владельцев, но не через скрытые SQL-связи.

ADR-002: Оркестрируемая saga с долговечными шагами

Статус: принято для учебного проекта. Дата: 2026-10-27.

Контекст

Процесс длится дольше HTTP-запроса, имеет дедлайны, человеческие задания и необратимую границу.

Варианты

Распределённая 2PC; хореография; оркестрация saga.

Решение

Incident сохраняет текущий шаг и commandId до отправки команды. После рестарта сверяет результат. До promote возможен атомарный abort; после promote завершаем вперёд.

Последствия

Прозрачный процесс и понятная защита. Incident усложняется и временно останавливает прогресс при отказе. 2PC не решает внешние действия и работу людей.

Когда пересмотреть

При добавлении независимых реакций события расширяются, но управление writer остаётся одним процессом.

ADR-003: At-least-once с outbox и inbox

Статус: принято для учебного проекта. Дата: 2026-10-27.

Контекст

БД и брокер не имеют общей транзакции. Падение между фиксацией состояния и публикацией может потерять факт.

Варианты

Публикация прямо после commit; 2PC; transactional outbox.

Решение

Локальная транзакция state + outbox, persistent RabbitMQ, confirms/mandatory, inbox + state перед ACK. REST readback сохраняет прогресс при задержке событий.

Последствия

Возможны дубли и задержка. Нужны очистка таблиц, метрики outbox/DLQ и проверка версий. Exactly-once end-to-end не заявляется.

Когда пересмотреть

Смена брокера не меняет требование доменной идемпотентности.

ADR-004: Один писатель и финальный checkpoint

Статус: принято для учебного проекта. Дата: 2026-10-27.

Контекст

Старые соединения и запоздалые команды способны писать после смены маршрута. Проверка lag до freeze устаревает.

Варианты

Только DNS; lease по часам приложения; подтверждённый долговечный fencing и монотонное epoch.

Решение

Контроллер блокирует A, дренирует запись, возвращает checkpoint. Data доказывает его применение на B. PROMOTE и RESUME сериализуются по generation и epoch; повтор команды возвращает прежний результат.

Последствия

В сетевой неопределённости возможен простой. Контроллер становится критическим доверенным компонентом. В production нужен адаптер, реально запрещающий старому writer запись; одного поля epoch в нашей БД недостаточно.

Когда пересмотреть

Если невозможно обеспечить fencing на уровне записи/хранилища, автоматический promote запрещён.

ADR-005: Плановый перенос и явные границы гарантий

Статус: принято для учебного проекта. Дата: 2026-10-27.

Контекст

Команда из трёх человек должна реализовать и показать отказы. Реальные платформы и физическое отключение слишком велики для MVP.

Варианты

Полноценная DR-платформа; подготовка с симуляторами; только уведомления.

Решение

Один workload, A/B, готовая реплика, симулятор инфраструктуры с устойчивым состоянием. Readiness выдаёт разрешение, не выключает оборудование. RPO=0 только после успешного планового барьера.

Последствия

Можно воспроизводить гонки и потери ответов. Демо не доказывает промышленную HA или безусловный RPO=0. Внезапная потеря источника — BLOCKED.

Когда пересмотреть

Перед production нужны испытания адаптеров, резервное копирование, HA управления, security review и согласованные RPO/RTO.

Источники и проектные допущения

Проверено 27 октября 2026. Источники подтверждают определения и поведение технологий, но не доказывают корректность нашего проекта.

  • C4 Container: уровень приложений и хранилищ, связи и технологии. Топология развёртывания описывается отдельно.
  • RabbitMQ confirms: подтверждение публикации и ACK потребителя решают разные задачи. Повторная доставка требует идемпотентности.
  • RabbitMQ reliability: повтор после неизвестного результата публикации может создавать дубли.
  • PostgreSQL standby: асинхронная передача журнала допускает окно потери данных при катастрофическом отказе источника.
  • OpenAPI 3.1: формат синхронных контрактов.
  • AsyncAPI 3.0: формат каналов, сообщений и операций.

Все значения дедлайнов, количество сервисов, выбранные состояния и поведение Simulation Adapter — наши проектные решения. Стек второй части предлагается командой, его запуск в первой части не выполнялся.
